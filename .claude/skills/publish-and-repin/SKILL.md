# Publish & Re-pin — keeping published numbers true

Numbers reach readers through three mechanically different surfaces. Two
staleness bugs and one population-attribution bug shipped from confusing
them (2026-07). Know which surface you're touching.

## The three surfaces

**1. `audit/article/fact_sheet.md` — LIVE §0–6, HAND-AUTHORED §7+.**
Regenerated by `scripts/build_article_factsheet.py` (each fact = label +
value + the exact SQL + ⚠caveats, via the `fact()` helper). It is NOT run by
`make fix` — regenerating it is a manual step after any rebuild ("Re-run
after any make fix" per its header). The script preserves everything from
the `"\n## 7."` marker onward verbatim (the hand-authored FedRAMP beats) —
never regenerate by hand-deleting the file, and keep new hand-authored
sections BELOW that marker.

**2. `audit/checks/check_article_guardrails.py` — the citability gates.**
Pytest assertions that pin article-critical claims to the DB (StateChat
enterprise-wide, DOJ coding tag, deployment-environment caveat still
warranted, stage_normalized populated, agentic sanity band, flagship
one-mention claims). When a rebuild legitimately moves a gated value,
re-baseline the gate in the SAME commit with the arithmetic in the comment.

**3. Deliberately-hardcoded dashboard copy.** Narrative pages pin literals
so figures can't drift from their citations mid-sentence — which means a
DB change makes them silently stale. The pinned inventory (grep-verified
2026-07-06; re-grep for old numbers whenever totals change):

| Location | What's pinned |
|---|---|
| `dashboard/app/stories/page.tsx` stat strip (~L101–121) | 2,133 → 3,660 filed; 527 → 1,005 GenAI; 44 → 248 enterprise rows; 70/4 coding; 1 Claude Code mention |
| `dashboard/app/stories/page.tsx` prose (~L722, ~L762) | coding-gap paragraph; "~900-row appendix" |
| `dashboard/app/experience/page.tsx` (~L704) | "~436 of 900 rows" banded-signal share |
| `dashboard/app/compare-years/page.tsx` (~L657) | "~900-row consolidated appendix" |

Home page and all `_view-model.ts` numbers are LIVE (verified) — don't
"fix" those by pinning.

## The population-attribution trap

Every count has a denominator population; conflating them is the recurring
bug class (a Claude Code mention on a consolidated Appendix-B row was
published as "in 3,660 use cases" — wrong population):

| Population | Count basis | Say |
|---|---|---|
| Individual filings | `use_cases` (3,660) | "individually-reported use cases" |
| Appendix-B grid | `consolidated_use_cases` (901) | "Appendix-B / consolidated entries" |
| Everything filed | both (4,561) | "filed entries" |
| Tag counts | `use_case_tags` with `use_case_id IS NOT NULL` vs not | match the fact-sheet SQL exactly |

When re-pinning a number, copy the fact sheet's SQL for it — the fact sheet
is the citation of record, and the guardrail checks are hand-synced to the
same queries.

## Verifying a published statistic (the tracing recipe)

Published number → which surface? →
- Dashboard live: page → `_view-model.ts` → `lib/db/**` query → run that SQL
  read-only against `data/federal_ai_inventory_2025.db`.
- Dashboard pinned: find it in the table above → find the matching fact in
  `fact_sheet.md` → re-run the fact's own SQL.
- Article claim: `fact_sheet.md` fact + its ⚠caveats (which MUST travel with
  the number) + the guardrail check that pins it.
If a number appears in none of these, treat it as unsourced and either wire
it to a fact or remove it.

## The post-rebuild publish sequence

1. `make fix` green ×2 (identical counts — idempotency) + full pytest.
2. `python3 scripts/build_article_factsheet.py`; confirm output says
   "preserved hand-authored §7+"; run
   `pytest audit/checks/check_article_guardrails.py -q`.
3. Grep the dashboard for the OLD headline numbers (both `3,660`-style and
   `3660`-style) and re-pin the table above; check population attribution on
   anything you touch.
4. Sync: `cp data/federal_ai_inventory_2025.db dashboard/data/`; verify
   `shasum` equal. (The dashboard `prebuild` hook also auto-syncs whenever
   `../data/...db` exists — a local `npm run build` can silently refresh the
   committed DB copy.)
5. `cd dashboard && npx tsc --noEmit && npm test && npm run build`.
6. **Runtime smoke — non-negotiable**: the Next build passes with broken
   SQL; SSG only exercises static routes. Start `next dev` (RESTART it if it
   was already running — it holds a stale sqlite handle across `cp`) and hit
   the dynamic routes: `/use-cases`, one individual detail slug, one
   consolidated slug, `/agencies/<abbr>`, `/analytics`, plus whatever you
   changed. Look up detail slugs/ids fresh from the DB — they rotate.
7. Commit DB + code together (never a DB-only or code-only push when both
   changed); push to `main` = production deploy; poll the production URL for
   the new headline number before declaring done.
